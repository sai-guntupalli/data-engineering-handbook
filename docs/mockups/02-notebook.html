Why Spark is lazy

Transformations such as filter, select and join do not run when you call them. Spark records each step in a logical plan and only executes when an action, such as count(), collect() or a write, forces it. That gives the optimiser the whole plan to reorder and prune before a single byte moves.

Mental model

Transformations build a plan. Actions run it. If no action is called, nothing runs.

Shuffles and stages

A shuffle happens whenever rows must move between executors so that equal keys meet: a groupBy, a join on unsorted data, a distinct. Every shuffle ends one stage and starts the next. Fewer shuffles almost always means a faster job.

  • Narrow transformations, like select and filter, stay inside a stage.
  • Wide transformations, like groupBy and join, force a shuffle.
  • Broadcasting a small table avoids shuffling the large side of a join.

Broadcast joins

When one side of a join fits in executor memory, Spark can send a copy to every executor and skip the shuffle entirely.

What to remember

  • Nothing runs until an action. Read the plan with explain() before tuning.
  • Each shuffle is a stage boundary, and usually the slowest part of a job.
  • Broadcast the small side of a join to keep the large side in place.

Check your understanding

Which of select, groupBy and collect starts a Spark job?

Only collect. It is an action. select and groupBy are transformations that add to the plan.

Why does a broadcast join avoid shuffling the large table?

Every executor already has a full copy of the small table, so each partition of the large table can be joined where it sits.
