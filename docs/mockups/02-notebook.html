Why Spark is lazy

Transformations such as filter, select and join do not run when you call them. Spark records each step in a logical plan and only executes when an action — count(), collect(), a write — forces it. That lets the optimiser reorder and prune work before a single byte moves.

Mental model

Transformations build a plan. Actions execute it. If nothing is an action, nothing runs.

In [3] 
# Build a lazy pipeline — nothing has executed yet
orders = spark.read.parquet("s3://lake/orders/")
paid   = orders.filter(orders.status == "paid")
daily  = paid.groupBy("order_date").agg({"amount": "sum"})

# The action is what triggers the job
daily.explain(True)
assert daily.count() > 0

Shuffles and stages

A shuffle happens whenever rows must move between executors so that equal keys meet — a groupBy, a join on unsorted partitions, a distinct. Each shuffle splits the job into a new stage. Fewer shuffles almost always means a faster job.

  • Narrow transformations (map, filter) stay inside a stage.
  • Wide transformations (groupBy, join) force a shuffle.
  • Broadcast small tables to avoid shuffling the large side.

Broadcast joins

When one side of a join fits in executor memory, Spark can ship it to every executor and skip the shuffle entirely.

In [7] 
from pyspark.sql.functions import broadcast

countries = spark.createDataFrame([("IN", "India"), ("US", "United States")], ["code", "name"])
joined = orders.join(broadcast(countries), "code")
assert "BroadcastHashJoin" in joined._jdf.queryExecution().executedPlan().toString()
